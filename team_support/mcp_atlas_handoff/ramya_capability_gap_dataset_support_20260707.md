# MCP-Atlas Capability-Gap Dataset Support

Date: 2026-07-07

Status: stable working note for team coordination. This is not a final dataset contract.

## Short Answer

MCP-Atlas is useful for generating candidate capability-gap examples, but it is not already a finished capability-gap dataset.

It provides tasks, enabled tools, reference trajectories, expected final-answer claims, and an evaluator. It does not directly provide labels such as `capability_gap=true`, gap type, critical failure step, or AgentRx-style failure categories.

## What MCP-Atlas Provides

The verified MCP-Atlas dataset fields are:

```text
TASK
ENABLED_TOOLS
PROMPT
GTFA_CLAIMS
TRAJECTORY
```

Runtime evidence from MCP-Atlas:

- `SandboxMCPClient.list_tools()` calls `/list-tools` and filters by `enabledTools`.
- `run_mcp_eval()` lists tools, gives transformed tool schemas to the model, then executes selected tool calls through `call_tool`.
- `mcp_evals_scores.py` evaluates final response coverage against `GTFA_CLAIMS`.

## What MCP-Atlas Does Not Directly Provide

MCP-Atlas does not directly label:

- whether a run contains a capability gap;
- what capability is missing;
- whether failure is caused by missing tools rather than model misuse;
- the critical failure step;
- AgentRx-style failure category labels.

The official evaluator compares expected final-answer claims with the model final answer. It does not directly compare the model trajectory to the gold trajectory and does not diagnose why the model failed.

## Candidate Gap Generation Pattern

A controlled capability-gap candidate can be generated by paired runs:

```text
Run A: original MCP-Atlas enabled tools.
Run B: same task, but one required tool or server is hidden.

If Run A succeeds and Run B fails, then Run B is a candidate induced capability-gap case.
```

This still requires validation, because a failed reduced-tool run can reflect:

- a true missing-capability gap;
- an active-registry exposure miss;
- ordinary model/tool-use failure;
- environment or server instability.

Recommended label levels:

```text
tool removal:
  the experimental condition hides a tool/server.

stable ablation failure:
  original run succeeds reliably and the ablated run fails reliably.

validated capability gap:
  stable ablation failure plus evidence that the removed capability is not reasonably replaceable by model knowledge, simple reasoning, or another visible tool.
```

## Suggested Team Message

```text
MCP-Atlas does not directly provide final capability-gap labels. It provides tasks, enabled tools, reference trajectories, and final-answer claim evaluation.

This handoff setup can help generate candidate capability-gap cases by running each task under original tools and controlled reduced/unavailable-tool conditions. If the original run succeeds but the reduced-tool run fails because a required capability was hidden, that becomes a candidate gap example.

AgentRx-style labels still need to be added separately: gap type, critical failure step, and evidence that the failure is due to missing capability rather than ordinary model/tool-use failure.
```

## Boundary

This note supports team coordination. It does not make MCP-Atlas a capability-gap dataset by itself.
